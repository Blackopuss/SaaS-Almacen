# SaaS-Almacen — reglas del proyecto

Contexto compartido por Claude Code y Codex. Leer antes de trabajar:

- `MEMORY.md`: decisiones confirmadas del fundador y estado real.
- `docs/PLAN_IMPLEMENTACION.md`: plan v0.6. Trabajar **un paso a la vez** (IDs como `BAS-01`, `INV-17`) y cerrar cada paso solo con su criterio «Listo cuando» verificado.

## Stack

- Next.js (App Router) + React + TypeScript estricto, `src/` como raíz de código, alias `@/*`.
- Tailwind CSS v4, shadcn/ui (BAS-12) y `motion` (Framer Motion) para animación. Respetar `prefers-reduced-motion`.
- MySQL 9.4 local (la misma versión que usará el fundador) con Prisma (BAS-03).
- npm como gestor de paquetes. Node >= 24.

## Reglas

- Interfaz en español (México). Código e identificadores en inglés; documentación y mensajes de commit en español.
- Las reglas de negocio viven en servicios de `src/modules/*` o `src/platform/*`, nunca en componentes.
- Cada consulta de negocio lleva contexto de empresa (`organization_id`): se hace con `forOrganization(ctx.organization.id)` de `@/server` (PLT-12), nunca con `db`. Toda tabla nueva con `organizationId` se agrega a `TENANT_MODELS`.
- Cantidades y dinero con decimal exacto; nunca `number` de punto flotante para stock o importes.
- Secretos solo en `.env.local` (ignorado por git). Plantilla sin secretos en `.env.example`.
- Antes de cerrar un paso: `npm run check` y `npm run build` deben pasar.
- Para UI usar las skills `ux-heuristics` (usabilidad: Krug y Nielsen), `impeccable` (`distill`, `critique`, `clarify`, `polish`), `ui-ux-pro-max` (sistema visual) y `web-design-guidelines` (revisión final). Todas en `.agents/skills` (enlazadas en `.claude/skills`). De `impeccable` solo se instalaron `SKILL.md` y `reference/`: su lanzador descarga un binario, así que se sigue su ruta «Launcher unavailable» (leer el contexto del proyecto directamente).
- **Sencillez (KISS) en la app** (`docs/ux/AUDITORIA_KISS.md`): cualquier persona debe poder usarla desde cero sin dar vueltas. Ver «Navegación y estados».

## Arquitectura (BAS-02)

```text
src/
  app/          Rutas y pantallas. Usa módulos y plataforma solo por su index.ts.
  components/   Componentes visuales compartidos.
  lib/          Utilidades sin reglas de negocio.
  server/       Infraestructura: cliente de base de datos y transacciones.
  platform/*    Núcleo compartido: auth, tenancy, authorization, entitlements, billing, audit, email, jobs, contacts, catalog.
  modules/*     Módulos contratables: inventory, purchasing (luego sales, crm).
```

| Desde | Puede importar |
| --- | --- |
| app | module, platform y lib (solo `index.ts`); components |
| module | otros module, platform y lib (solo `index.ts`); server; components |
| platform | otra platform y lib (solo `index.ts`); server. **Nunca** módulos |
| server, components | lib (`index.ts`) |

Dentro de un mismo módulo o área se usan imports relativos libremente. `eslint-plugin-boundaries` lo impone y `npm run lint:boundaries` lo demuestra con casos temporales.

## Base de datos (BAS-03)

- Prisma 7.10 (versiones exactas) con `@prisma/adapter-mariadb`. Cliente generado en `src/server/generated/` (ignorado; se genera en `postinstall`). `npm overrides` fuerza versiones corregidas de `mariadb`, `mysql2`, `deepmerge-ts` y `handlebars`.
- Usuarios: `almacen_app` (solo SELECT/INSERT/UPDATE/DELETE, lo usa la aplicación en `src/server/db.ts`) y `almacen_migrator` (DDL, lo usa la CLI de Prisma vía `prisma.config.ts`). `root` solo para `npm run db:setup`.
- Bases: `almacen_dev`, `almacen_test`, `almacen_shadow`.
- Comandos: `setup`, `db:setup`, `db:migrate`, `db:deploy`, `db:status`, `db:check`. **`db:reset` borra datos: nunca ejecutarlo sin consentimiento explícito del fundador** (Prisma también lo bloquea para agentes).
- Para operar sobre la base de pruebas: `DATABASE_NAME=almacen_test npm run db:deploy`.
- Si `prisma migrate dev` pide confirmación (no interactivo): crear `prisma/migrations/<UTC>_<nombre>/migration.sql` con `npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`, revisar el SQL, aplicar con `npm run db:deploy` (y en `almacen_test`) y `npm run db:generate`.

## Pruebas (BAS-07)

- `npm test` corre `unit` (`src/**/*.test.ts`) e `integration` (`*.int.test.ts`). Requiere MySQL local corriendo.
- Una prueba que importe `@/platform/*`, `@/modules/*` o `@/server` (aunque no consulte la base) se llama `*.int.test.ts`: carga el cliente de base de datos y debe correr en el proyecto secuencial. `unit` queda para código puro (`src/lib`, catálogos, reglas). Integración corre en hilos (`pool: "threads"`).
- Una base de pruebas propia para un worktree se llama `almacen_test_<x>` (`DATABASE_TEST_NAME=almacen_test_<x>`; se crea con `DATABASE_NAME=almacen_test_<x>_dev DATABASE_TEST_NAME=almacen_test_<x> node scripts/db-setup.mjs`). Agentes en paralelo: cada uno con su worktree, su base y su puerto.
- La integración usa siempre `almacen_test` (nunca dev): migra y vacía tablas al iniciar. Fixtures con DDL usan `migratorConnection()` de `tests/setup/test-db.ts`; el código bajo prueba usa `db` (usuario de la app).

## Sistema visual (BAS-12)

- Fuente de verdad: `design-system/almacen/MASTER.md` (generado con `ui-ux-pro-max`). Estilo Minimal & Swiss, claridad tipo Apple, modo claro por defecto. Tipografía Inter.
- Modo oscuro gris neutro (zinc) y monocromo: las acciones son blancas sobre zinc y el color queda para estados: clase `dark` en `<html>` aplicada antes de pintar por `THEME_SCRIPT` (layout raíz) y cambiada con `useTheme`/`setTheme` de `src/components/theme.ts` (clave `almacen-tema`, claro por defecto) y el interruptor `ThemeToggle` (barra lateral y encabezado móvil). Todo color nuevo necesita su valor en `:root` y `.dark`.
- Tokens en `src/app/globals.css` (`primary #2563EB`, `success`, `warning`, `destructive`…). Nunca colores sueltos en componentes. Cambiar un token exige que pase `src/components/design-tokens.test.ts` (contraste WCAG: texto ≥ 4.5:1, bordes/anillos ≥ 3:1).
- shadcn/ui (base Radix, preset nova) en `src/components/ui`, ajustado: objetivos táctiles ≥ 44 px en móvil, textos en español, avisos con Sonner (`toast.success/error`).
- Animaciones que dependen de «reducir movimiento» se eligen con CSS (`motion-reduce:`), no con `useReducedMotion`, para que servidor y cliente generen el mismo HTML.
- Animación con `motion` (`src/components/motion.tsx`): presets cortos, salida más rápida que entrada, `reducedMotion="user"`.
- Formularios: `FormField` (etiqueta, ayuda y error enlazados con `aria-describedby`) y `PasswordInput`; Server Actions con `useActionState` y validación Zod en el servicio de `platform`/`modules`.
- **Accesibilidad (PIL-07):** `npm run verify:a11y` (con `npm run dev` activo y la cuenta demo; `UI_BROWSER=chromium` si no hay Edge) pasa axe-core WCAG 2.1 A/AA sin fallas graves ni críticas, sin desbordamiento, con foco visible en cada parada de teclado y objetivos táctiles ≥ 44 px en móvil, en cada pantalla principal y en los detalles de producto, orden y conteo; y comprueba que un formulario enviado vacío lleva el foco a un error explicado. Una pantalla nueva del menú o un flujo principal se agrega a `SCREENS`. Las pantallas de error usan `retry()` (vuelve a pedir al servidor), no `reset()`; `src/app/global-error.tsx` cubre una falla del layout raíz en español.
- `/sistema-visual` (solo desarrollo) muestra los componentes. Con `npm run dev` activo (puerto 3000 por defecto, `UI_BASE_URL` para otro), `npm run verify:ui` comprueba foco visible, diálogo accesible, tamaños táctiles y desbordamiento en móvil y escritorio (Edge instalado).

## Navegación y estados (BAS-13)

- Pantallas de la app en `src/app/(app)/` con `AppShell`: barra lateral en escritorio; en móvil, barra inferior con 4 secciones y «Más». Secciones en `src/components/app-shell/nav.ts`, cada una con su `module` para ocultarla si no está contratado (MOD-05). El menú tiene solo lo que se usa seguido (Inicio, Inventario, Movimientos, Conteos, Compras, Configuración); lo que se configura una vez vive dentro de Configuración (Ubicaciones, con `also` en `nav.ts` para marcar la sección). Una sección nueva no entra al menú sin una razón de uso diario.
- Estados reutilizables en `src/components/states.tsx`: `PageHeader`, `EmptyState`, `ErrorState`, `LoadingState`, `PageContainer`. Cada sección tiene `loading.tsx` y `error.tsx` compartidos.
- No mostrar botones deshabilitados sin explicación; una acción aparece cuando su paso está implementado.
- **Reglas KISS de pantalla** (auditoría `docs/ux/AUDITORIA_KISS.md`):
  - Encabezado: como mucho **dos** botones, para lo de todos los días (verbo + sustantivo: «Registrar entrada»). Lo ocasional va en una fila de enlaces bajo el título, nombrados por lo que hacen («Cambiar de lugar», «Corregir existencias»), sin frases de explicación al lado. Lo raro (exportar, archivados) va en enlaces discretos al pie de la lista.
  - Sin descripción bajo el título si solo repite el nombre de la sección. Ayudas de campo de una línea, solo si evitan un error; si una etiqueta necesita explicación, se cambia la etiqueta.
  - Una sola forma de hacer cada cosa: la salida es siempre `/movimientos/salida-rapida` («Registrar salida», uno o varios productos); no agregar otra pantalla para lo mismo. El nombre de un enlace es el título de la pantalla a la que lleva.
  - Listas: la fila completa abre el detalle (enlace con `after:absolute after:inset-0`); las acciones viven en el detalle, no en botones pequeños por fila. Nada de botones con solo un ícono.
  - Filtros que se usan poco van plegados (`<details>` «Más filtros»), abiertos solo si hay uno aplicado. Datos administrativos (cupo del plan) no ocupan el Inicio: aparecen solo como aviso cuando requieren atención.

## Despliegue (BAS-09..11, ADR 0024)

- Servidor (hoy una EC2 con Ubuntu 26.04): Caddy (HTTPS) → `next start` en 127.0.0.1:3000 y el worker como servicios de systemd (cuenta `almacen`), MySQL 9.4 en Docker solo en 127.0.0.1. Guía del fundador: `docs/DESPLIEGUE.md`.
- `deploy/instalar.sh` (idempotente: nunca cambia secretos ni datos), `deploy/empaquetar.sh` (build en GitHub Actions; el workflow «Desplegar» lo manda por SSH), `deploy/bin/desplegar` (paquete con suma verificada o build en el servidor; versiones en `releases/`, respaldo verificado antes de migrar, vuelta automática si la salud falla), `volver`, `respaldo` (restauración de prueba + cifrado con `age`), `restaurar` y `almacen <comando>`.
- **Migraciones solo de expansión**: nada que borre o renombre algo que la versión anterior use; eso va en un despliegue posterior (así `volver` funciona sin tocar la base).
- Desplegar = `git push origin pruebas:produccion` con un commit que ya pasó CI (workflow «Desplegar»: build en GitHub, paquete por SSH). Nunca empujar a `produccion` algo que no esté en verde en `pruebas`.
- Una variable de entorno nueva de producción se agrega a `deploy/plantillas/env.production` (y a `.env.example`). Un cambio en `deploy/` lo prueba el workflow «Despliegue de prueba» en un Ubuntu limpio; no subirlo sin revisar que pase.

## Convenciones de código

- **Servicios** en `src/platform/*` o `src/modules/*`, con `import "server-only"`. Reciben datos ya separados (`input`, `headers`) y devuelven uniones de resultado para fallos esperados (`{ ok: true } | { ok: false; reason/fieldErrors }`); lanzan solo ante lo inesperado (`AppError` y subclases de `src/lib/errors.ts`, o `console.error` + respuesta genérica).
- **Validación** con Zod en el servicio; mensajes en español listos para mostrar.
- **Pantallas**: Server Component que llama `requireSession()` + componente cliente con `useActionState`; acción en `actions.ts` con `"use server"` que solo traduce `FormData` ↔ servicio y hace `redirect`/`revalidatePath`.
- **Pruebas**: unitarias junto al código (`*.test.ts`); integración en `tests/<área>/*.int.test.ts` contra `almacen_test`, con correos únicos por corrida (`algo.${Date.now()}@example.test`) y `afterAll(() => db.$disconnect())`. Pruebas lentas por scrypt: dar `timeout` explícito. Para ordenar filas creadas en la misma prueba usar `id` (UUIDv7, en orden), no `createdAt`: dos líneas pueden compartir milisegundo (pasó en VAL-05). Comportamiento visible: agregar casos a `scripts/verify-ui.mjs` (no crear datos persistentes salvo la cuenta demo; usar IPs de prueba con `X-Forwarded-For`).
- **IDs** UUIDv7 (`newId`), fechas `DATETIME(3)` UTC, cantidades con `Decimal`.
- **Verificación manual en navegador sin tocar desarrollo:** `npm run dev:test` levanta la app en `http://localhost:3100` contra `almacen_test` y `npm run test:company -- "<contraseña>" [rol]` crea ahí una empresa con plan y una cuenta para entrar. Esa base se vacía en cada `npm test`, así que no hay que limpiar nada; úsalo siempre que el flujo cree filas que ya no se pueden borrar (bitácora, versiones de presentación, movimientos).
- **Datos de prueba creados en `almacen_dev`** durante verificaciones manuales: borrarlos al terminar. Excepción: la bitácora es solo-agregar (ADR 0006), así que una empresa creada en dev ya no se puede borrar; evitar crear empresas en verificaciones manuales.
- **Server Action nueva (PLT-15):** agregarla a `REVIEWED` en `tests/isolation/server-actions.int.test.ts` (qué recibe, de dónde sale la identidad, qué prueba cubre el caso entre empresas); la prueba falla si falta. Nunca tomar `userId` u `organizationId` del cliente: salen de `requireSession`/`requireOrganizationContext`.
- **Better Auth por HTTP (PLT-15):** solo los enlaces de correo pasan por `/api/auth/*` (lista de permitidos en `src/platform/auth/http.ts`). Los flujos nuevos se hacen con Server Actions + `auth.api`; un enlace de correo nuevo se agrega a la lista con su prueba.
- **Roles y permisos (USR-01):** la matriz aprobada `docs/MATRIZ_ROLES_PERMISOS.md` es la fuente de verdad; el catálogo está en `src/platform/authorization/catalog.ts` y `catalog.test.ts` falla si no coinciden. Cambiar un permiso = cambiar ambos (y una migración si se agrega un rol: `CHECK` en `membership_role`). El titular no es un rol.
- **Autorización (USR-02):** una sola decisión, `can(subject, permission)` de `src/platform/authorization/policy.ts` (pura, denegar por defecto). En servidor: `requirePermission("modulo.recurso.accion")` (sesión + empresa + permiso; lanza `ForbiddenError`) o `getAccess()` para preguntar `access.can(...)`; en servicios, `assertAllowed(organizationId, userId, permission)`. Los roles se leen de la base en cada petición; sin membresía activa no hay permisos, ni para el titular.
- **Reservado al titular (USR-03A):** contratar, cancelar, método de pago, cambiar plan/módulos y transferir usan `requireOwnerAction(permiso)` / `assertOwnerAction(organizationId, userId, permiso)`; el permiso debe estar en `OWNER_ONLY_PERMISSIONS` (lo que ningún rol concede).
- **Equipo y titularidad (USR-03B):** todo cambio de roles, desactivación o invitación pasa primero por `checkTeamChange`/`checkInvitationRoles` de `src/platform/authorization/team-rules.ts` (mensajes en `TEAM_RULE_MESSAGES`). `Organization.ownerUserId` solo cambia en `acceptOwnershipTransfer` (`ownership.ts`), con bloqueo `FOR UPDATE` de la empresa.
- **Invitaciones (USR-04):** el token de un enlace nunca se guarda ni se registra: solo `hashInvitationToken(token)`. Se exportaron `blockedFor`/`recordAttempt`/`throttleKeys` desde `@/platform/auth` para limitar flujos fuera de `auth`.
- **Aceptar invitación (USR-05):** el correo de la membresía sale siempre de la invitación, nunca del formulario. Para crear cuentas fuera del registro normal usar `prepareInvitedAccount` + `insertInvitedAccount` dentro de la transacción del llamador.
- **Cambios de equipo (USR-06):** las operaciones sobre miembros pasan por `withTeamChange` de `team.ts` (bloqueo de empresa + reglas + transacción); no escribir `membership_role` desde otro lugar.
- **Pantalla de equipo (USR-08):** acciones en `src/app/(app)/configuracion/equipo/actions.ts`; persona y empresa salen de `requireOrganizationContext()`. Un diálogo que se cierra tras una Server Action lo hace dentro de la acción envuelta en `useActionState` (no con `setState` en un efecto: lo prohíbe ESLint).
- **Pantalla nueva (USR-09):** empieza con `const access = await getAccess(); if (!access.can("…")) return <PageContainer><NoAccessState /></PageContainer>;` y, si va en el menú, lleva el mismo permiso en `nav.ts`. Botones y enlaces de una acción se pintan solo si `access.can(...)`; la Server Action lo comprueba otra vez en su servicio.
- **Casos negativos (USR-10):** al construir algo que menciona un caso `NEG-xx` de la matriz, escribir su prueba y actualizar `NEGATIVE_CASES` en `tests/platform/negative-by-role.int.test.ts` (quitar `waitsFor`, agregar el archivo).
- **Acción de bitácora nueva (USR-11):** agregar su frase en español a `AUDIT_ACTION_LABELS` (`src/platform/audit/trail.ts`); `team-audit.int.test.ts` falla si falta.
- **Módulos (MOD-01/02, ADR 0007):** cada módulo declara su contrato en `src/modules/<módulo>/contract.ts` con `defineModule` y se agrega a `src/modules/registry`; la plataforma nunca importa módulos, recibe ids o contratos.
- **Modelo comercial (MOD-03, ADR 0008):** nunca modificar `plan_version`/`plan_module_price` (la base lo rechaza): crear versión nueva y mover `plan_offer`. Lo que una empresa puede usar se lee de `entitlement`, no de la suscripción.
- **Derechos (MOD-04):** quien escriba en `entitlement` llama `invalidateEntitlements(organizationId)` después de confirmar; para decidir cupos usar `getFreshEntitlements`.
- **Guard de módulo (MOD-05):** pantallas de un módulo empiezan con `const access = await getModuleAccess()` y comprueban `access.can("…")` y `access.hasModule("…")`; los servicios de módulo llaman `assertModulePermission(organizationId, userId, permiso)`; las altas que consumen cupo llaman además `assertWithinLimit`.
- **Activar módulos (MOD-06):** solo con `activateModule`/`deactivateModule` pasando `moduleRegistry` de `@/modules/registry`; nunca escribir derechos de módulo a mano fuera de pruebas y del sembrado de desarrollo.
- **Cupos (MOD-07):** toda alta o reactivación que consuma un límite llama `consumeQuota(tx, organizationId, "active_products")` dentro de su misma transacción y aborta si `ok` es falso; archivar llama `releaseQuota`. Nunca contar filas para decidir si cabe.
- **Transacciones (MOD-08):** dentro de una transacción no usar `db`, `forOrganization` ni servicios que abran otra conexión (p. ej. `getEntitlements`): todo con el cliente `tx`. Para límites, `readLimit(tx, organizationId, clave)`. Todo lo que sume una persona a una empresa llama `lockOrganization` + `assertSeatAvailable` en su transacción.
- **Consola interna (MOD-09, ADR 0009):** toda pantalla y acción bajo `src/app/interno` empieza con `requirePlatformStaff()`; los servicios que actúan sobre cualquier empresa vuelven a comprobar `isPlatformStaff`. Formularios con `useActionState`: devolver `values` al rechazar para no perder lo escrito.
- **Solo lectura (MOD-11):** un permiso nuevo que no modifica nada debe terminar en `.read` o `.export` (o ser `*.export.create`) para seguir disponible con el plan vencido; cualquier otro se trata como escritura. Pantallas de módulo: `access.moduleState(...)` → `none` muestra `NoModuleState`, `read_only` muestra `ReadOnlyNotice` y oculta las acciones de escritura.
- **Productos (INV-02):** las altas solo por `createProduct`; el actor (`{ organizationId, userId }`) sale siempre de la sesión. Un fallo esperado dentro de una transacción se saca con una excepción propia (ver `Rejected`) para que todo se revierta, cupo incluido.
- **Unidades (INV-05):** agregar o cambiar una unidad = `UNITS` en código + migración que actualice la tabla `unit`. Una tabla sembrada por migración se agrega a `REFERENCE_TABLES` en `tests/setup/global-db.ts`.
- **Cantidades (INV-06):** toda cantidad capturada pasa por `parseQuantity` con la regla del producto (`unitCode`, `quantityStep`); nunca `Number()` ni redondeos. Componentes cliente no importan `@/platform/*`: las opciones (unidades, precisiones) se arman en el servidor y se pasan como props (ver `unit-options.ts`).
- **Conversión (INV-09):** todo movimiento convierte su captura con `resolveConversion(tx, productId, captura)` dentro de su transacción y guarda cantidad capturada, factor, versión de presentación y cantidad base; el navegador solo manda lo tecleado y el id de la presentación.
- **Listas (INV-10):** toda lista que puede crecer se pagina en la base (`skip`/`take` + `count`, orden estable terminado en `id`, sobre un índice que empiece por `organizationId`); la página va en la URL (`?pagina=`) y una fuera de rango muestra la última. Ver `listProducts`.
- **Búsquedas (INV-11):** el texto pasa por `normalizeSearch` y cada palabra se busca con `contains` escapando `%`, `_` y `\` (Prisma no lo hace); las columnas buscadas deben estar en el índice que ordena la lista. Formularios de búsqueda o filtro: `Form` de `next/form` con `GET`, estado en la URL (`?q=`), sin Server Action.
- **Filtros (INV-12):** un filtro de la URL solo se aplica si su valor está entre las opciones de la empresa (`listProductFilterOptions`); lo desconocido se ignora. `sin` = sin categoría / sin marca. Los enlaces de página y «Quitar filtros» se arman con `pageHref`, que conserva búsqueda y filtros. Selects que aplican al elegir: `FilterSelect` (envía su formulario; el botón sigue sirviendo sin JavaScript).
- **Ubicaciones (INV-13, ADR 0010):** `src/platform/locations`. Todo lo que cree una empresa (servicio, script o fixture) llama `ensureDefaultLocation(tx, organizationId)` en la misma transacción; en pruebas, `createTestOrganization` de `tests/setup/organization.ts` en vez de `db.organization.create`. Los scripts importan `@/platform/locations/bootstrap`, no el `index.ts`. La ubicación por defecto es `isDefault: true` (las demás `NULL`, nunca `false`).
- **Jerarquía de ubicaciones (INV-14, ADR 0011):** tipos fijos `ZONE` > `AISLE` > `SHELF` con nombres libres; una ubicación solo va dentro de un tipo más amplio (`canContain` de `kinds.ts`), por eso no hay ciclos. Todo cambio pasa por los servicios de `hierarchy.ts` (bloquean la instalación; no escribir `location` desde otro lugar). Nunca se borra una ubicación (disparador): se archiva. Para mostrar dónde está algo, la ruta de `listLocations` («Zona A › Pasillo 2»). Las opciones de selectores (dónde va, qué tipo cabe) se arman en el servidor y se pasan como props.
- **Corregir una migración ya aplicada:** nunca editarla; agregar otra migración. Un `CHECK` solo rechaza lo falso: con columnas que admiten `NULL` usar `COALESCE` para que la expresión no quede «desconocida». Si una migración falla en `almacen_test` (queda a medias y `npm test` deja de arrancar), reparar esa base y marcarla con `DATABASE_NAME=almacen_test npx prisma migrate resolve --applied <nombre>`.
- **Existencias (INV-15, ADR 0012):** el saldo (`stock_balance`) solo cambia junto con un movimiento (`stock_movement` + `stock_movement_line`) en la misma transacción; movimientos y líneas son inmutables (disparadores) y se corrigen con reversa. Una línea = un producto, una ubicación, `IN` u `OUT`, con lo capturado, factor, versión de presentación y cantidad base (lo que devuelve `resolveConversion`). Los servicios de movimientos van en `src/modules/inventory`; sus pruebas, en `tests/inventory/`, terminan comprobando `expect(await reconcileStock(organizationId)).toEqual([])`.
- **Movimientos (INV-16):** servicios en `src/modules/inventory/movements.ts`. Todo movimiento empieza con `lockRows(tx, "product", ids)` de `@/server` (bloquea las filas de la empresa en orden; así los cambios de un producto ocurren uno tras otro y el saldo leído es el vigente), convierte con `resolveConversion`, escribe movimiento + línea(s) y actualiza `stock_balance`, todo en la misma transacción. El cliente de empresa sigue sin SQL directo: `lockRows` es la única excepción y pone el filtro de empresa. Cantidades para mostrar: `formatStock(cantidad, unitCode)`; nunca `Number()` sobre existencias. El movimiento es su propio rastro (autor, fecha, motivo): no se duplica en la bitácora salvo ajustes y reversas.
- **Captura con presentación (INV-17):** el formulario manda solo `capture` (`base`, `p:<id de presentación>` o `u:<código de unidad>`) y la cantidad; el servicio arma el `Capture` y lee el contenido vigente. La equivalencia que se muestra antes de confirmar viene de `previewEntryAction` (servidor), nunca se calcula en el navegador.
- **Transacciones con bloqueo (INV-19B):** toda transacción que bloquea (`lockRows`, o una actualización usada como candado) y luego decide con lo que lee se abre con `LOCKING_TRANSACTION` de `@/server` (READ COMMITTED): con el nivel por defecto de MySQL la transacción sigue viendo los datos de su primera lectura aunque haya esperado el candado, y decidiría con información vieja. Además, tomar los candados antes de leer. Quien archiva un producto o una ubicación bloquea su fila; los movimientos bloquean producto y ubicación. Orden fijo de candados para que no haya interbloqueos: instalación → ubicación, producto → ubicación, y varios productos siempre ordenados por id (`lockRows` lo hace).
- **Verificación antes de confirmar:** encadenar con `set -o pipefail && npm run check 2>&1 | tail … && git commit`; sin `pipefail` el `tail` oculta el fallo y el commit sale con pruebas rotas (pasó en INV-19).
- **Pantalla nueva:** cada `page.tsx` llama `getModuleAccess()`/`getAccess()` por sí misma (lo exige `navigation.int.test.ts`), aunque delegue el resto en un componente compartido.
- **Salidas (INV-19):** `registerExit` comparte el núcleo `post` de `movements.ts` con entradas y saldo inicial (un producto, una ubicación, `IN`/`OUT`); el saldo se resta con `updateMany` condicionado (`quantity >= cantidad`) y el `CHECK` de la tabla queda como última defensa. Las pantallas de entrada y salida son `MovementScreen` (`kind`); una operación nueva de una línea agrega su entrada en `KINDS` (servicio y pantalla) y su modo en `EntryForm`.
- **Saldo inicial (INV-18):** es un movimiento `INITIAL` (`registerInitialBalance`), permitido solo mientras el producto no tenga otro tipo de movimiento y una vez por ubicación; nunca escribir `stock_balance` directo. Los formularios de cantidad reutilizan `EntryForm` (`mode`) y `captureOptions` de `src/app/(app)/movimientos/`.
- **Selects tras un envío rechazado:** React reinicia el formulario al terminar su acción y un `<select value=…>` controlado se queda mostrando la primera opción. Usar `defaultValue` + `key` que cambie con cada respuesta (contador `answers` **dentro del estado** que devuelve la acción envuelta en `useActionState`, `{ ...respuesta, answers: prev.answers + 1 }`; ver `EntryForm` y `AddLocationDialog`). Nunca con un `useState` aparte: un `setState` después de un `await` se aplica solo, antes que la respuesta, y reconstruye el select con los valores viejos (pasó en el mapeo de columnas), y devolver siempre lo escrito cuando el servicio rechaza.
- **Reintentos (INV-21):** todo formulario que confirma un movimiento manda `idempotencyKey` (el servidor lo crea con `newId()` al pintar la pantalla y `EntryForm` lo lleva oculto); un servicio nuevo de movimientos busca la clave tras tomar sus candados y antes de validar.
- **Respuesta perdida (INV-22):** una Server Action que confirma algo irreversible se llama dentro de `try/catch` en el cliente, con `unstable_rethrow(error)` primero y después la verificación por clave; nunca se deja reintentar a ciegas.
- **Ajustes (INV-24):** la línea de un ajuste guarda la diferencia en la unidad del producto (factor 1); lo contado y lo anterior van en la bitácora. Un tipo de movimiento que exige motivo lleva también su `CHECK` en `stock_movement`.
- **Reversas (INV-25):** corregir un movimiento es reversarlo (y registrar el correcto), nunca editarlo; la reversa copia las líneas del original. Una migración que agrega una regla (`CHECK`, índice único) a una tabla con datos debe pensarse contra lo que ya existe en desarrollo.
- **Historial (INV-27):** las listas de movimientos con filtros usan `listMovements` (nunca consultas propias); una fecha de filtro es un día del calendario de la empresa (`organization.timeZone`), no de UTC. Filtro nuevo = parámetro en la dirección + campo en `applied` + `pageHref`.
- **Salida rápida (INV-28):** un movimiento de varias líneas valida todas antes de escribir y devuelve `lineErrors` por posición; bloquea todos sus productos con una sola llamada a `lockRows` (orden fijo) y descuenta cada saldo una vez con la suma de sus líneas. El formulario manda las líneas como JSON (`lines`) con ids y texto tecleado; nunca factores ni existencias.
- **Lector (INV-29):** un cuadro que recibe lecturas no se deshabilita ni descarta texto mientras espera al servidor: encola (`enqueue`/`drain` en `quick-exit-form.tsx`) y aplica las respuestas sobre la lista más reciente (`latest`), no sobre la del render que inició la búsqueda. Enter lee `event.currentTarget.value`.
- **Mínimos (INV-30):** «bajo» se deriva del saldo en cada consulta (`listLowStock`); no guardar banderas ni contadores de existencias bajas. El mínimo se valida con `parseQuantity` y la regla del producto; los archivados no cuentan.
- **Conteos (INV-31):** capturar no escribe movimientos ni saldos. Cada operación sobre un conteo bloquea primero el producto (si lo hay) y luego el conteo (`lockRows(tx, "stockCount", …)`), y comprueba que siga `OPEN`. La referencia de un producto (`countedAt`, `systemQuantity`) se fija en su primera captura y no se mueve con las siguientes. Tabla nueva de empresa = también su dato de ejemplo en `tests/isolation/two-companies.int.test.ts`.
- **Conteo y movimientos posteriores (INV-32):** nunca comparar lo contado con el saldo de hoy. Diferencia = contado − `systemQuantity`; movido después = saldo de hoy − `systemQuantity`; objetivo = saldo de hoy + diferencia. Si el objetivo es negativo no se aplica: se recuenta.
- **Aplicar conteos (INV-33):** el estado del conteo, leído bajo su candado, es la guarda de idempotencia; la clave `count:<id>` es la segunda. No usar `useTransition` como candado de un envío: sigue pendiente hasta que la pantalla se repinta y descarta lo que llegue mientras; usar una bandera propia (`busy` en `capture-form.tsx`).
- **Reconciliación (INV-34):** una diferencia entre saldo e historial es un defecto que se investiga; ninguna tarea ni pantalla «repara» saldos por su cuenta. Comprobar con `npm run stock:reconcile` (o `DATABASE_NAME=almacen_test npm run stock:reconcile`), que también compara el valor de cada producto con existencias × costo promedio (`reconcileValue`, VAL-04). Un caso de aceptación nuevo de la fase 1 se agrega a `phase1-cases.int.test.ts`.
- **Inicio (INV-35):** un bloque nuevo del panel se pinta solo si `access.can(...)` de su sección y reutiliza el servicio de esa sección; el panel no tiene consultas propias. Solo lleva lo que pide atención hoy (existencias bajas, últimos movimientos, guía de primer uso); el plan aparece solo como aviso. La barra inferior móvil admite cuatro secciones (`mobile: true` en `nav.ts`).
- **Trabajos en segundo plano (IMP-01, ADR 0013):** encolar con `enqueueJob(tx, organizationId, …)` dentro de la transacción del cambio que lo origina; el tipo es `modulo.accion` en minúsculas y su manejador se agrega a `src/modules/registry/jobs.ts`. Un manejador puede correr dos veces: debe ser idempotente (usar `context.jobId` como clave) y trabajar solo con `forOrganization(context.organizationId)`. En el `payload` van ids y opciones, nunca secretos ni la empresa.
- **Archivos (IMP-02, ADR 0014):** todo archivo de un cliente pasa por `storeFile` con un propósito de `FILE_PURPOSES` (agregar ahí uno nuevo con sus permisos de la matriz); nunca escribir en disco desde otro lugar ni usar el nombre del archivo como ruta. Para descargar, `createFileLink` y un enlace normal a su `url`; no servir archivos desde `public/` ni devolverlos en una Server Action. Quien procesa un archivo usa `readStoredFile(organizationId, fileId)` con la empresa de la sesión o del trabajo.
- **Hojas de cálculo (IMP-03):** todo CSV o XLSX que salga del sistema se escribe con `buildCsv`/`buildXlsx` de `@/platform/files` (celdas de texto y fórmulas neutralizadas con `'`); no concatenar CSV a mano. Una columna nueva de importación se agrega a `IMPORT_COLUMNS` con su ayuda y ejemplo. Las descargas van por una ruta `GET` bajo `/api/…` que llama `requireOrganizationContext()` y responde `attachment` + `nosniff` + `no-store` (y se agrega a `PROTECTED` en `proxy.ts`).
- **Leer archivos de clientes (IMP-04):** siempre con `readSpreadsheet` de `@/platform/files`; nunca evaluar fórmulas ni abrir otras partes del archivo, y nunca `Number()` o `parseFloat` sobre una celda: los números pasan por `normalizeDecimal(texto, separadorElegido)` y luego por las reglas de cantidad. Los números de fila que se muestran son los del archivo. Opción fija dentro de un `NativeSelect` que también recibe una lista: darle `key` (React avisa si falta).
- **Validar importaciones (IMP-05):** una regla nueva de fila va en `validateImportRows` con su mensaje listo para mostrar y la columna a la que pertenece; la validación nunca escribe (ni su resultado) y la confirmación volverá a validar. Lo que dependa de lo que ya existe en el catálogo (clave existente, código de barras ocupado, cupo) pertenece a la clasificación (IMP-06), no a esta revisión.
- **Clasificar importaciones (IMP-06):** todo paso posterior a la revisión empieza con `checkImport(actor, importId)`, nunca con datos guardados de una revisión anterior. Las claves se comparan sin distinguir mayúsculas ni acentos (`foldName`), como la base. Mostrar cupo «requerido / disponible» no lo garantiza: decirlo en pantalla y apartar solo al confirmar.
- **Confirmar importaciones (IMP-07):** el cupo de una importación se aparta solo con `reserveQuota(tx, …)` dentro de la transacción que la marca `CONFIRMED`, con la fila bloqueada (`lockRows(tx, "productImport", …)`); cada alta posterior usa `confirmReservation` y lo no usado se devuelve con `releaseReservation`. La lectura del archivo va antes de la transacción; lo que no puede estar viejo (el cupo) lo decide el contador.
- **Aplicar importaciones (IMP-08):** el worker trabaja solo con los `product_import_item` fijados al confirmar, nunca vuelve a leer el archivo ni a clasificar. Un paso nuevo por producto va dentro de la transacción del lote, antes de marcar el elemento `DONE`, y debe poder repetirse sin efecto. Un script que importe el `index.ts` de un módulo se corre sin `--conditions=react-server` y con el gancho de `scripts/worker.mts` para `server-only`.
- **Liberar lo retenido (IMP-08B):** un trabajo que aparta algo (cupo, reservas) declara `onFailed` en su manejador para devolverlo cuando el trabajo falla en definitiva; lo llama `settleFailedJobs` (el worker, cada 30 s y tras cada fallo), puede repetirse y nunca corre mientras el trabajo siga vivo. Una importación solo se cierra con `cancelImport`, `releaseFailedImport` o `stopUnauthorizedImport` (`import-release.ts`), siempre con su fila bloqueada: devuelven `reservedPlaces` y lo dejan en 0 en la misma transacción. Un trabajo que actúa a nombre de una persona vuelve a comprobar su permiso antes de cada lote (NEG-20).
- **Existencias importadas (IMP-09):** las existencias del archivo entran como movimientos `INITIAL` (`postImportedStock`, uno por fila con existencia, clave `import:<elemento>:<n>`) dentro de la transacción del lote, con las cantidades fijadas al confirmar; nunca se vuelve a convertir con la presentación vigente. Lo que puede impedirlo se comprueba con `checkImportedStock` **antes** de tocar el producto, para que un producto que falla quede entero como estaba. El lote bloquea de una vez sus productos existentes y luego sus ubicaciones (orden producto → ubicación). Una operación nueva que haga un archivo agrega su permiso a `importPermissions`: se exige al confirmar y otra vez antes de cada lote.
- **Salidas importadas (IMP-10):** un archivo de salidas pasa por `startExitImport` → `reviewExitImport`/`checkExitImport` (relee y revalida, nunca escribe) → `confirmExitImport` (fija las filas y encola `inventory.import_exits`) → `applyExitImport` en el worker. Lo que impide descontar dos veces es el folio: `exitKey(productId, folio)` se guarda en `exit_import_row.appliedKey` (único por empresa) **solo** al registrar la salida, en la misma transacción que el movimiento; una fila cuya clave ya existe queda `DUPLICATE` y no mueve nada. No usar otro mecanismo para deduplicar ni escribir `appliedKey` desde otro lugar. A diferencia de los saldos iniciales, una salida se convierte al registrarla (`resolveConversion`), con la presentación vigente. «Hasta qué fecha está actualizado el stock» es `getExitCoverage` (derivado de las filas aplicadas, sin banderas guardadas). Las fechas de un archivo son días del calendario (`DATE`), se leen con `parseExitDay` (año-mes-día o día/mes/año, nunca mes/día) y se muestran con `formatExitDay`.
- **Exportaciones (IMP-11):** todo archivo que sale con datos de la empresa se arma en `buildExport` (`src/modules/inventory/exports.ts`): pide `inventory.export.create` **y** el permiso de lectura de lo que contiene (exportar no da más que la pantalla), lee por páginas con tope `EXPORT_MAX_ROWS`, escribe con `buildCsv`/`buildXlsx` y deja una línea en la bitácora. Una exportación nueva se agrega a `EXPORT_KINDS` con su permiso de lectura; una columna que no todos pueden ver (costos, CMP-16) se omite según el permiso, no se deja vacía a medias. La descarga es un enlace o un `<form method="get">` normal hacia `/api/exportaciones/<tipo>` (no `next/form`: la respuesta es un archivo, no una pantalla).
- **Guía de primer uso (IMP-12):** `getFirstSteps` deriva los pasos de lo que existe (hay productos, hay existencias, hay un movimiento que no es saldo inicial); no guardar banderas de «paso hecho» ni de «guía cerrada». Un paso nuevo se agrega ahí y en `FirstStepsGuide`, con sus acciones ofrecidas solo según `access.allows(...)`.
- **Contactos (CMP-01, ADR 0016):** proveedores y clientes son la misma tabla `contact` de `src/platform/contacts`, con facetas `isSupplier`/`isCustomer` (al menos una). Un módulo trabaja solo con su faceta y con sus permisos (`purchasing.supplier.*`); una tabla que apunte a un contacto usa la relación compuesta y su servicio comprueba la faceta. El RFC se guarda en mayúsculas y sin espacios, o `NULL` (nunca `''`). Un `CHECK` debe ser una expresión booleana: `col IS NULL OR …`, no `COALESCE(REGEXP_LIKE(…), TRUE)` (MySQL lo rechaza y la migración queda a medias).
- **Proveedores (CMP-02):** servicios en `src/platform/contacts/suppliers.ts` (`createSupplier`, `updateSupplier`, `getSupplier`, `listSuppliers`); todos filtran `isSupplier: true`, así que un contacto que solo es cliente no se alcanza desde Compras. El RFC pasa siempre por `normalizeRfc` (mayúsculas, sin espacios ni guiones, forma y fecha válidas). Un posible duplicado (mismo RFC o mismo nombre en la empresa) **se advierte, no se prohíbe**: el servicio responde `reason: "duplicate"` sin guardar y solo guarda si llega `acceptDuplicates`; un formulario que lo use muestra los contactos parecidos y un botón «Guardar de todos modos» (`name="acceptDuplicates" value="1"`). Pantallas bajo `/compras/proveedores`, con `access.moduleState("purchasing")`.
- **Contadores de cupo (IMP-S13):** dentro de una transacción no usar `createMany({ skipDuplicates })` (`INSERT IGNORE`) para «asegurar» una fila que luego se actualiza: al encontrarla deja un candado compartido y dos transacciones se interbloquean al actualizar. Crear la fila donde nace su razón de ser, bajo un candado (los contadores, en `provisionCompany` con `ensureQuotaRows`), y en el camino normal leer antes de insertar. Una prueba que falla «a veces» por interbloqueo es un defecto que se investiga, no una prueba que se repite.
- **Producto-proveedor y costos (CMP-03, ADR 0017):** servicios en `src/modules/purchasing/product-suppliers.ts`; pruebas de Compras en `tests/purchasing/`. El último costo **no se captura a mano**: lo escribe `recordLastCost(tx, …)` dentro de la transacción de una compra, tras comprobar `purchasing.cost.record`. Todo dato de costo se lee solo si la persona tiene `purchasing.cost.read`: el `select` de Prisma no incluye esas columnas para los demás y el campo no existe en la respuesta (nunca devolverlo vacío u ocultarlo en la pantalla). Un servicio nuevo que devuelva costos sigue ese patrón (`mayReadCosts`) y agrega su caso a `NEG-04`. Un id que va a parar a una dirección de `redirect` se limpia antes (`idPath`).
- **Órdenes de compra (CMP-04, ADR 0018):** servicios en `src/modules/purchasing/orders.ts`. Todo lo que cambia una orden empieza con `lockDraft(tx, orderId)` dentro de `inDraft` (bloquea la fila con `lockRows(tx, "purchaseOrder", …)`, `LOCKING_TRANSACTION`, y rechaza si ya no es borrador); un estado nuevo o una transición (CMP-05) parte del mismo candado. Una línea se resuelve con `resolveConversion` dentro de la transacción y guarda capturado, presentación, **versión**, factor y base; el formulario manda solo `capture` (`base` o `p:<id>`) y lo tecleado. El costo de una línea viaja solo si el formulario lo trae (lo pinta el servidor según `purchasing.cost.record`): `undefined` no lo toca, vacío lo borra. Importes y total se calculan con decimales exactos, nunca se guardan ni se redondean. Un mensaje de error del servicio se asigna a su campo por lo que significa, no por una palabra suelta (un «presentaciones» mandó el error de cantidad al campo equivocado).
- **Estados de la orden (CMP-05):** la única tabla de transiciones es `PURCHASE_ORDER_TRANSITIONS` de `src/modules/purchasing/order-states.ts` (pura, con prueba unitaria); servicios y pantallas preguntan `canTransition`/`transitionProblem`, y el disparador `purchase_order_transition` repite la misma tabla en la base: cambiar una exige cambiar la otra (migración nueva) y `order-transitions.int.test.ts`. Una transición hecha por una persona bloquea la orden (`lockOrder`), responde `repeated` si ya estaba ahí y deja bitácora; las que hace una recepción usan `advanceOrderOnReceipt(tx, …)` dentro de su transacción. Las líneas de una orden que ya no es borrador **no se escriben** (disparadores): lo recibido se guardará en tablas de recepción, nunca en `purchase_order_line`. «Confirmar orden» significa que la persona la da por enviada; mandar el correo (CMP-06B) no cambia el estado por sí solo.
- **PDF (CMP-06A, ADR 0019):** todo PDF que salga del sistema se arma con `PdfPageWriter` + `buildPdf` de `@/platform/files` (texto escapado, sin contenido activo, Windows-1252); no agregar una librería de PDF ni escribir bytes de PDF desde otro lugar. Para alinear o partir renglones usar `textWidth`/`wrapText`, no contar caracteres. Un documento nuevo sigue a `order-pdf.ts`: permiso propio de exportar, lectura por el mismo servicio que la pantalla (así los costos salen solo para quien puede verlos), ruta `GET` bajo `/api/…` con `attachment` + `nosniff` + `no-store`, bitácora, y una prueba que extraiga el texto del archivo y compruebe su tabla de objetos.
- **Correo a terceros y envíos (CMP-06B, ADR 0020):** un correo que tarda o puede fallar no se manda desde una Server Action: se pide (renglón propio + `enqueueJob` en la misma transacción) y lo manda el worker; el renglón dice cómo terminó y el manejador declara `onFailed` para cerrarlo. `sendEmail` rechaza cabeceras con saltos de línea y adjuntos fuera de lo permitido (`InvalidEmailError`: no se reintenta); una plantilla nueva con nombres escritos por un cliente los aplana a una línea (`oneLine`) y, si va a alguien que no es usuario, pone `replyTo` a la persona que lo envía. El destinatario sale siempre de un dato guardado y validado, nunca del formulario. Lo que la gente lee de un fallo es un motivo propio, no el error del servidor de correo. Para ver un fallo en local: correo terminado en `.invalid`. La orden se envía con `requestOrderDelivery`; mandar el correo no cambia su estado.
- **Recepciones (CMP-07, ADR 0021):** servicios en `src/modules/purchasing/receipts.ts`; la entrada de inventario la escribe `postReceiptEntry(tx, …)` de Inventario (movimiento `RECEIPT`) dentro de la misma transacción que la recepción y el estado de la orden. Candados: productos → ubicación → orden. Lo pendiente se cuenta en los términos de la línea de la orden (cajas pedidas − cajas recibidas, `purchase_receipt_line.capturedQuantity`); lo que entra se convierte con el contenido vigente al recibir. Recepciones y sus líneas son inmutables (disparadores) y un movimiento `RECEIPT` no se reversa desde Inventario (NEG-22): se corrige con una devolución (CMP-12). Clave de confirmación obligatoria (`purchase_receipt.idempotencyKey`) y verificación por clave si la respuesta se pierde (`checkReceiptAction`). Recepción parcial (CMP-08): el servicio recibe `lines` (`orderLineId` + lo tecleado en los términos de la línea; vacío o 0 = no llegó) y valida cada cantidad con `parseQuantity` (presentaciones completas; paso del producto) y contra lo pendiente leído bajo el candado de la orden (nunca más de lo que falta, NEG-24); los errores por línea vuelven en `lineErrors` por id de línea de la orden. La orden queda `PARTIAL` mientras falte algo y `RECEIVED` cuando no falta nada. Destino por línea (CMP-09): cada línea puede traer su `locationId` (si no, la de la recepción); `postReceiptEntry` bloquea todas las ubicaciones de una vez y lleva el saldo por producto + ubicación. La pantalla muestra el contenido vigente de la presentación (`contentText`) y el de la orden cuando cambió (`orderedContentText`); entra el vigente. Reintentos (CMP-10): una clave repetida solo es reintento si coincide persona, orden y lo pedido (`sameReceipt`); si no, `KEY_REUSED`. Pruebas de concurrencia en `receipts.int.test.ts` con `Promise.all` sobre el servicio real. Cierre con faltante (CMP-11): `closePurchaseOrder` (`order-close.ts`), solo desde `PARTIAL`; el faltante se deriva (pedido − recibido), no se guarda. Archivar un producto consulta `openOrdersFor` (órdenes `SENT`/`PARTIAL` con algo pendiente); todo lo que confirme o reciba una orden bloquea antes sus productos. Devoluciones (CMP-12): `returnToSupplier` (`returns.ts`) por recepción; la salida la escribe `postReturnExit` (movimiento `RETURN`) con el factor de la línea de recepción, nunca con el vigente; lo devuelto se suma con `returnedByLine` bajo el candado de la orden y nunca pasa de lo recibido. Un movimiento de un documento de Compras (`RECEIPT`, `RETURN`) no se reversa desde Inventario. Último costo (CMP-13): lo escribe la recepción (`recordReceivedCosts` → `recordLastCost`) con el costo de la línea de la orden; el permiso `purchasing.cost.record` se consulta antes de abrir la transacción. Sugerencias (CMP-14): `suggestions.ts` (`plan` deriva todo de mínimos, saldos y órdenes abiertas; no se guarda nada); generar recibe solo ids de productos, los bloquea y vuelve a calcular; «en camino» incluye borradores. Reportes (CMP-15): `reports.ts` (`getPendingReport`, `getPurchasesBySupplier`, `buildPurchaseReport`); un reporte o archivo nuevo de Compras lee por el mismo servicio que la pantalla y agrega sus columnas de importe solo si `purchasing.cost.read` (nunca vacías a medias). Guard de Compras (CMP-16): `tests/purchasing/module-guard.int.test.ts` llama cada función exportada por `@/modules/purchasing` en una empresa sin el módulo; un servicio nuevo se agrega a su lista (o a `NOT_SERVICES` si corre dentro de la transacción de otro) y debe empezar con `assertModulePermission`. Quitar un módulo (CMP-17): `provisionCompany(..., { openWork: moduleOpenWork, acceptOpenWork })` avisa del trabajo a medias de cada módulo que se quita (`src/modules/registry/open-work.ts`); un módulo con pendientes nuevos agrega ahí su función. Nunca se cancela ni se borra nada al quitar un módulo: queda en solo lectura.

Cancelar = devolver todo lo que queda y marcar la venta (`CANCELLED`, una vez, con motivo). `sale_return` y sus líneas son inmutables (disparadores). Tras confirmar, la pantalla vuelve a la venta con `?devolucion=<id>`, que dice cuánto entregar.
- **Historial de ventas (VEN-22):** `listSales`/`listSaleCashiers` (`src/modules/sales/history.ts`, `sales.sale.read`), pantalla `/ventas/historial` con filtros en la dirección (`q` = número de venta o palabras del nombre del cliente, `desde`/`hasta` días del calendario de la empresa con `startOfDay` de Inventario, `cajero`), orden por número descendente. La sección «Ventas» del menú pide `sales.sale.read`: quien solo consulta (Consulta) entra y `/ventas` lo manda al historial; el mostrador sigue pidiendo `sales.sale.create`.
- **Reportes de ventas (VEN-23):** `getSalesReport`/`buildSalesReport` (`src/modules/sales/reports.ts`, `sales.report.read`/`.export`), pantalla `/ventas/reportes` (`vista` = `dias`, `productos` o `cajeros`; por omisión este mes) y descarga `GET /api/ventas/reportes/<tipo>`. Todo se deriva de ventas, líneas y devoluciones (ventas canceladas fuera, devoluciones descontadas); el total es lo que pagó el cliente con IVA. La ganancia (antes de IVA, al `unitCost` de cada línea) solo si `mayReadInventoryCosts`: sin ella el campo y la columna no existen; un producto vendido sin costo conocido lleva `costUnknown` en vez de una ganancia. Tope `SALES_REPORT_MAX` con `truncated`.
- **Cotizaciones (COT-01):** `sales_quote` (número consecutivo por empresa, cliente obligatorio con faceta de cliente, `validUntil` como día del calendario, regla de IVA y descuento copiados, notas; estados `DRAFT`, `SENT`, `ACCEPTED`, `REJECTED`) y `sales_quote_line` (como `sale_line`, sin ubicación ni costo). No toca existencias ni caja. Los totales no se guardan: salen de las líneas con `saleTotals`. «Vencida» no es un estado guardado: una enviada cuya vigencia pasó se lee como vencida. Disparadores: nace borrador; número y autor no cambian; lo que ofrece (cliente, vigencia, IVA, descuento, notas) y sus líneas solo cambian en borrador; no se borra. Bloqueo: `lockRows(tx, "salesQuote", …)`.
- **Hacer cotizaciones (COT-02):** solo `createQuote`/`updateQuote` (`src/modules/sales/quotes.ts`, `sales.quote.create`); se leen con `getQuote`/`listQuotes` (`sales.quote.read`) y el total mientras se escribe sale de `previewQuote`. Precios con `priceLines` del carrito (sin pedir existencias ni caja), IVA de `readTaxRule` y descuento con `checkDiscount`: en una cotización no hay autorización, así que pasar el tope de quien cotiza o quedar bajo el costo sin permiso se rechaza. Vigencia por omisión hoy + 15 días (`QUOTE_DEFAULT_DAYS`), de hoy a un año, en días del calendario de la empresa (`calendar.ts`). Editar un borrador bloquea la cotización, cambia sus líneas y vuelve a poner precio con lo vigente. Pantallas `/ventas/cotizaciones` (lista, `nueva`, `[id]`, `[id]/editar`), enlazadas desde la fila de enlaces de Ventas.
- **PDF y envío de cotizaciones (COT-03):** `quote-pdf.ts` (`composeQuotePdf`/`buildQuotePdf`, con `sales.quote.read`: la cotización no lleva costos) encabezado con el nombre de la empresa (no hay logotipo guardado), marca «BORRADOR»/«VENCIDA»/«RECHAZADA» y «No es un comprobante fiscal»; descarga `GET /api/ventas/cotizaciones/<id>/pdf`. El correo sigue a CMP-06B en `quote-delivery.ts`: `requestQuoteDelivery` (`sales.quote.create`) bloquea la cotización, pasa un borrador a `SENT` en la misma transacción, toma el correo de la ficha del cliente y encola `sales.send_quote` con `sales_quote_delivery`; `deliverQuote` (worker) vuelve a revisar el permiso de quien lo pidió. No se envía una aceptada, rechazada o vencida. El correo del cliente se guarda con `setCustomerEmail` (`@/platform/contacts`, `sales.customer.create`).
- **Estados de la cotización (COT-04):** la única tabla es `QUOTE_TRANSITIONS` de `quote-states.ts` (pura, con prueba unitaria: borrador → enviada → aceptada o rechazada) y el disparador `sales_quote_transition` la repite; cambiar una exige cambiar la otra. Las personas usan `markQuoteSent` (entregada sin correo), `acceptQuote` y `rejectQuote` (con motivo) de `quote-status.ts` (`sales.quote.create`): bloquean la cotización, responden `repeated` si ya estaba ahí y dejan bitácora. Una vencida (enviada con su día pasado, se deriva) no se acepta pero sí se rechaza; un borrador con la vigencia pasada no se marca enviado.
- **Pedidos (COT-05):** `sales_order` + `sales_order_line` (estados `OPEN`, `PARTIAL`, `FULFILLED`, `CANCELLED`; un pedido por cotización, índice único `quoteId`). Solo `convertQuoteToOrder` (`sales-orders.ts`, `sales.quote.create`) los crea: bloquea la cotización, exige `ACCEPTED`, copia precios, descuento, IVA y notas tal como se aceptaron (aunque los precios cambien después) y responde `repeated` con el pedido existente. Disparadores: nace abierto de una cotización aceptada y para su cliente; lo acordado no cambia; líneas inmutables; no se borra. Se leen con `getSalesOrder`/`listSalesOrders` (`sales.quote.read`); pantallas `/ventas/pedidos` y `/ventas/pedidos/[id]`. Un pedido **no aparta existencias** (COT-06, ADR 0030): lo pedido sigue a la venta en el mostrador hasta que se surte; surtir valida lo que hay en ese momento.
- **Rendimiento (PIL-06):** `npm run load:test` contra la app compilada en `almacen_test` (ver `docs/PRUEBA_CARGA.md`); una pantalla nueva de uso diario se agrega a `screens()` del script. Meta: p95 < 500 ms con 20 personas en los modos `solo` y `real`.
- **Reportes con tope:** un reporte que suma datos con tope de filas los lee en orden fijo y devuelve `truncated`; la pantalla avisa que los totales están incompletos (CMP-S11).
- **Bitácora (PLT-14):** todo cambio sensible de empresa llama `recordAuditEvent(clienteDeLaTransacción, { organizationId, actorUserId, action, target, reason })` dentro de la misma transacción; eventos de cuenta con `recordSecurityEvent`. Nunca pasar secretos en `metadata` (igual se depuran).

## MFA (PLT-08A..PLT-09)

- Complemento `twoFactor` de Better Auth en `auth.ts`; servicio `src/platform/auth/mfa.ts` (`getMfaStatus`, `startTotpEnrollment`, `confirmTotpEnrollment`); panel `MfaPanel` en `/configuracion`; QR con el componente `QrCode` (`uqr`).
- `getCurrentSession` toma la cookie de `cookies()` (no de `headers()`) para ver la sesión rotada dentro de la misma Server Action.
- Inicio de sesión con MFA: `signIn` devuelve `reason: "mfa"` → `/verificar-codigo` (`verifySignInCode`; cada código sirve una vez). MFA obligatoria según `isMfaRequired` (`mfa-policy.ts`, hoy: titulares; agregar administradores y personal de plataforma cuando existan). `requireSession()` redirige a `/activa-dos-pasos`; solo esa pantalla y `mfaSetupAction` pasan `allowMissingMfa`.
- Cuenta demo: MFA activa con `DEMO_TOTP_SECRET` (`npm run db:seed`); código con `npm run demo:codigo`; helpers en `scripts/totp.mjs`. `verify:ui` entra calculando códigos nuevos (por eso tarda ≈2.5 min).
- Códigos de recuperación (PLT-09): generador y normalización en `backup-codes.ts`; `regenerateBackupCodes` y `disableMfa` en `mfa-recovery.ts`; `verifySignInCode({ method: "backup" })`. Se muestran una sola vez con `BackupCodesList`. Desactivar está prohibido si `isMfaRequired`.
- Si una Server Action cambia la cookie de sesión, Next vuelve a pintar la pantalla: el aviso de éxito va en un componente que siga montado (ver `MfaPanel`).
